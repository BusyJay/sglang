# mmap 协同路由的真实 trace 回放（2026-10-21）

重放 `verify_reuse_diagnosis_20261018/service/verify-routes.jsonl.gz` 中四个真实
请求。每个请求从空专家 cache 起步，先跑 128 个完整 sweep，再统计共
57,408 次 target verify 层调用；每次 3 token、top-10。回放器从当前
`qwen38_hybrid_plan.cuh` 提取 planner 主体并编译执行，搬运量按当前
`qwen38_hybrid_device.py` 的单块 mmap 布局和仅在 CPU 路由时发布请求的
协议计算。原始 trace、规划器和设备协议的 SHA256 在 JSON 的
`provenance` 中。

当前没有匹配这条新路径的完整 CPU/GPU 成本标定。生产选择器使用空表时，
57,408 次调用都走全 GPU，**mmap 请求写入和 CPU 结果读取均为 0**。
下表中的 1/2/3 是诊断性的“最多选这么多个 LFU rejected 专家”假设，
每种模式独立重放缓存演化，不代表当前生产选择器会作出的决定。

JSON 还包含 6,390 和 6,643 slot、逐请求结果及分项字节数。所有预算与
CPU 上限组合的 GPU fill 次数都和此前的回放完全一致。

在这段 trace 中，每次 CPU 层的 GPU→映射内存写入为 **15,612 字节**：
12 字节请求头、15,360 字节 BF16 激活、120 字节路由 ID、120 字节
FP32 路由权重。随后 GPU 从映射内存读 **30,720 字节** FP32 CPU 结果。
单块 mmap 至少容纳 46,332 字节，按系统 4 KiB 页取整为 48 KiB。
全 GPU 层既不写请求头，也不写激活、ID、权重，GPU 结果 kernel 也不读
映射结果。6,388 slot、最多 1 CPU 专家的回放里，有 5,208 次 CPU 层
前面紧跟着至少一个静默跳过的全 GPU 层。

旧报告按有 CPU 样本就对每层回读 route 来估计，导致最多 1 CPU 专家
时额外计了 6.57 MiB route D2H；新协议不再执行这项全层回读。
实际 CPU 参与的层会把全部 route ID 写入 mmap，合计 4.33 MiB，
已经包含在上表的请求写入中。GPU 专家权重填充仍走原有 H2D 路径。
结果回传现在是 GPU 直接读取映射内存，不再是每层单独的结果 memcpy。

这些是按源码访问宽度统计的**逻辑 payload 字节数**，不是实测 PCIe
transaction、带宽或耗时；CPU native、CUDA 和服务端到端均未运行。
trace 不包含 prefill、draft、resize、初始生产 cache 或动态预算变化。
CPU 上限越大而 CPU 层调用数下降，是不同模式缓存演化造成的，不能
据此判断 CPU 计算更快。
